Research preview

Orchestration for scientific agents.

Published evaluations of multi-agent workflows report several-fold higher token use, coordination failures, errors that propagate between steps, and completion claimed without evidence. On sequential tasks, a single agent can outperform them.

MAESTRO converts a research request into a plan of steps, agents and checks, and executes it within a budget set in advance. A result is accepted only when its checks, evaluated in code, pass on the tool outputs it cites. Irreversible steps require approval and run at most once, including after a crash.

Meta-orchestration

Coordination across independent agents.

Requesting agents define the question and provide the tools. MAESTRO designs the graph of steps and agents, executes it and checks the result.

Signed requests

Requests are signed with Ed25519 and checked against the scopes each requester is allowed.

Approval before execution

Jobs from all agents share one queue. No plan runs until it is approved.

MCP and A2A

Tools connect over MCP, including long-running tasks. Steps can be delegated to remote agents over A2A once their Agent Cards are verified.

Result delivery

A checked result is returned to the requesting agent or forwarded to another. A result that fails its checks is not delivered.

Resource allocation

Spending caps per agent by week or month, priorities between agents, and a single pause for all jobs.

Delegation to orchestrators

A step can be delegated to another orchestrator with its own budget, deadline and acceptance checks.

Plan design

From request to validated plan.

A request in natural language is converted into a plan, validated, and approved before execution.

Five block types

Step, each (parallel map), decide, repeat (bounded) and approve.

Up to three candidate plans

Each with a cost ceiling, a time estimate and a count of irreversible calls. A single-agent plan at equal budget is always included.

Three design methods

A fitted predictor; reuse of a plan that passed on the same request; or tree search over simulated copies of the tools, selecting from the cost–pass-rate Pareto front.

Communication topology

Within a team, which agent reads whose output is designed: lead–workers, chain, debate, review or vote. Links that do not improve results are removed.

Model assignment and batching

A model is assigned to each step. Parallel work is batched to the concurrency each instrument declares.

Validation

Each block is checked in code as it is drafted. The complete plan is compiled and validated before execution.

Adaptive execution

Plan revision at step boundaries.

Between steps and rounds, the unexecuted part of a plan can be revised. Every revision is validated against the approved plan.

Repair before redraw

A local edit to the failed part is tried first. If it fails, the remaining plan is redrawn. The job can also stop early and return its best result.

Triggers

Checks that still fail after retries, out-of-range results, a projected budget overrun, an unresponsive tool, diminishing gains, or a note from you or the requesting agent.

Three invariants

The approved answer fields and checks are retained, completed work is unchanged, and the revised plan passes the same validation. Revisions outside the approved scope require approval.

Recursive decomposition

A step that keeps failing becomes a sub-plan, up to three levels deep, within the step's remaining budget.

Long-running campaigns

Jobs that last days to weeks.

While an experiment or simulation runs, the job is suspended and holds no process or worker slot.

Suspend and resume

The process exits while waiting and resumes from a checkpoint when the result is due. The cost of resuming does not grow with campaign length.

Restart- and upgrade-safe

Each job keeps the plan version it started with. Submitted tasks are polled, never resubmitted.

Interim results

After each round, the best result so far is evaluated with the same checks as the final result.

Recoverable interruptions

An expired credential or a retired model becomes a question for you, or a model substitution within the approved budget.

Instrument concurrency

Tools declare how many calls they accept at once, for example four reactors. Plans are batched accordingly.

Simulated clock

Time can be accelerated to rehearse a full campaign in seconds before instrument time is booked.

Integrity

Provenance, verification and safety.

Checks, budgets and policies are enforced in code, outside the language models. Every result records its inputs.

Journal

Every model call, tool call and verdict is recorded. A run resumes after a crash without repeating model calls.

Standard formats

Lineage exports as W3C PROV (PROV-JSON, PROV-O); traces as OpenTelemetry.

Retraction

Withdrawing a measurement flags every result derived from it and proposes re-runs.

Verification

Evidence requirement

A result is accepted only with a certificate citing the tool outputs behind each claim.

Rule-based checks

Eleven check types, including table lookups, numeric tolerances and rankings. A model judge runs only after the rule-based checks pass.

Check validation

Each check is run against a deliberately wrong answer to confirm that it can fail.

Judge agreement

Agreement between the model judge and expert verdicts is reported as a percentage and as Cohen's κ.

Injection testing

Canary runs insert instructions into tool outputs and record whether the agent follows them.

Custom verifiers

Deterministic or simulation-based verifiers can be added. A check can route the next step: explore, replicate or finish.

Safety

Budgets

Tokens, cost, time, tool calls and instrument hours are reserved before execution. Stop conditions are enforced in code.

Irreversible actions

Each tool declares its side-effect class. Irreversible actions require approval and run at most once. Outcomes left uncertain by a crash are referred to you.

Policy and risk tiers

A Cedar policy is evaluated before every action with external effects, under four risk tiers. At high tiers, runs are repeated three times, must agree, and results are signed.

Signatures and pinning

Requests and results are signed with Ed25519, content carries trust labels, and tool definitions are pinned by hash.

Sandboxed execution

Code runs in a sandbox whose network and file-system isolation is tested before use.

Injection and fault tolerance

A quarantined reader, taint tracking and an attack suite of about 30 cases address prompt injection. Circuit breakers and fault injection address cascading failures.

Automation

Scheduled and event-driven jobs.

Triggers

Jobs run on a schedule, or when a file changes, a source has new items, or a webhook is called.

Incremental processing

A repeating job makes no model calls when its inputs are unchanged, and records which items it has processed.

Graduated autonomy

Automatic actions are off by default. Write access is granted after verified report-only runs and revoked after failures.

Prompt optimisation

Judge questions and instructions are revised and tested on held-out cases. You adopt or roll back each change.

Export and monitoring

Loops export as LOOP.md and SKILL.md. Health metrics, a watchdog, and webhook or email notifications are included.

Console

All jobs in one list, each showing its result first, with a live plan graph and follow-up questions.

Learning

Designer improvement, tested on held-out data.

The plan designer is revised from its own results. Each candidate revision is evaluated on a held-out test set that the designer can neither read nor modify.

No weight updates

Lessons from each round update a playbook and the designer's instructions. A revision is adopted only if it outperforms the current version twice on a hidden held-out test at equal budget.

Learned plan models

A small structure model, then a fine-tuned language model, trained only on data MAESTRO generates. Each is used only if it outperforms the prompted designer on the hidden test.

Public benchmarks

RSI Bench and RSI-Index, with MAESTRO's hidden test, are run from the console.

Applications

Current use cases.

Polymer electrolytes

A self-driving-lab planning agent defines the objective and constraints. MAESTRO designs and checks each round's plan, and the lab executes the approved experiments.

CO₂-reduction catalysts

From one sentence and a catalyst table, three candidate plans were drafted. The selected plan's shortlist passed all six of the requester's checks.

Direct-air-capture sorbents

A sorbent shortlist in which each claim cites a published paper.

Oxygen-evolution catalysts

A partner agent requested a screen of 14 NiFe oxyhydroxide surfaces. MAESTRO called the partner's tools, and its checks determined when the screen was complete.
